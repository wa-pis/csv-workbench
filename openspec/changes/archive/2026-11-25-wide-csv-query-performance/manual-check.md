## Контрольный CSV

Создан отдельный временный `manual-wide.csv`: **600 строк данных × 4000 столбцов**, **247 005 190 байт**, SHA-256 `ad6fd50de169e04f87f8dbcb28645a8ab6818fdf0d5de2363323d01f6738c37f`.

- Заголовки: `n0`…`n3999`.
- `n0`: идентификаторы `000001`…`000600`.
- `n1`: `keep` для нечётных идентификаторов, `other` для чётных.
- `n2`: маркер исходного идентификатора строки.
- `n3`: пустая строка при `i % 3 == 1`, `Привет` при `i % 3 == 2`, NULL при `i % 3 == 0`, где `i` — исходный идентификатор 1…600.
- Остальные столбцы: `1234567890`, повторённое 10 раз, то есть 100 ASCII-цифр.

Это новый ручной fixture с различимыми строками и значениями, а не источник 242 422 890 байт из [backend-замеров](benchmarks.md). Сохранение и экспорт выполнялись в отдельные временные `manual-saved.csv` и `manual-view.csv`.

## Подтверждено через интерфейс

1. `manual-wide.csv` открыт в автономной сборке. Начальный буфер содержал **200 строк**; NULL и пустая строка отображались по-разному.
2. В первой строке `n0` изменён на `a-ёж`. Команда Go to Row для строки **599** догрузила буфер до **400 строк**; её `n0` изменён на `z-ёж`.
3. Фильтр `n0 contains ЁЖ` и сортировка `n0 DESC` дали две строки в порядке **`z-ёж`, `a-ёж`**. Это одновременно подтверждает выборку по правке ранее неподгруженной строки и поиск без учёта регистра для кириллицы.
4. Во второй строке отфильтрованной и отсортированной таблицы `a-ёж` заменено на `zz-ёж`. Представление обновилось без экспорта/повторного открытия и переставило строки в порядок **`zz-ёж`, `z-ёж`**. Маркеры `n2` соответствовали исходным строкам **000001** и **000599**, то есть правка сохранила идентичность строки после сортировки.
5. Скрыт `n1`; в представлении осталось **3999 столбцов**.
6. Save As записал `manual-saved.csv`, состояние стало clean. После сброса выборки были показаны **4000 столбцов**, начальный буфер **200 строк** и полный набор из **600 строк**.
7. Export CSV записал `manual-view.csv`; приложение показало сообщение **`Exported 2 rows.`**

## Проверка записанных файлов

Отдельная проверка файлов через CLI подтвердила фактическое содержимое на диске:

- **Save As:** все **600 строк × 4000 столбцов** в исходном порядке, включая скрытый `n1` и строки вне фильтра. Единственные изменения `n0` — `zz-ёж` у исходной строки 1 и `z-ёж` у строки 599. Для каждой строки проверено сохранение `n1`, `n2`, `n3` и остальных значений, включая различие NULL/пустой строки.
- **Экспорт выборки:** **2 строки × 3999 столбцов**, без скрытого `n1`, в ожидаемом порядке **`zz-ёж`, `z-ёж`**. Проверено совпадение полей с соответствующей проекцией эффективных исходных строк.
- **Исходный `manual-wide.csv`:** SHA-256 после проверки совпал с исходным; файл не изменился при Save As и экспорте.

Это проверка правильности записи, а не новые замеры времени, RAM или временного диска.

## Найденное расхождение unique

В таблице unique первое отображённое `Value` оказалось **`zz-ёж`** вместо ожидаемого **`000002`**. Отдельная backend-проверка дала правильные первые значения **`000002`, `000003`, `000004`**. Следовательно, по этому прогону нельзя объявить отображение unique в приложении корректным, даже при правильном backend-результате.

Для исправления открыт отдельный этап `fix-projected-csv-edit-overlay`. Исправление UI и его повторная ручная проверка не входят в подтверждённый результат сборки `3aaaa24`; последующий результат должен фиксироваться отдельно с идентификацией проверенного bundle.

## Активная отмена не подтверждена

Предпринята попытка отмены на источнике **600 × 4000**, но операция успела завершиться до следующего accessibility-наблюдения. Активное прерывание сортировки/unique не было наблюдено. Завершение операции до нажатия или чтения состояния **не засчитывается как успешная отмена**; отсутствие позднего результата именно отменённой операции этим прогоном также не подтверждается.

Сценарий требует повторения без подмены worker и с наблюдаемой отменой выполняющейся задачи. Backend-замер отмены подготовки payload из `benchmarks.md` не заменяет эту ручную проверку.

## CI и оставшиеся проверки

В исходном CI для `3aaaa24` Windows остановился на тестовом ожидании POSIX-режима файла. Проверка режима исправлена отдельным коммитом **`3f9d56f`**: тест учитывает реально поддерживаемый Windows режим назначения. [Повторный CI](https://github.com/wa-pis/csv-workbench/actions/runs/45891799570) завершился успешно на Windows, Linux, macOS Intel и Apple Silicon. Код приложения в этом коммите не менялся; ручной прогон выше относится к исходному ARM-артефакту `3aaaa24`.

Не подтверждены: исправленное отображение unique в новой сборке и активная ручная отмена сортировки/unique. Новые замеры на 5/20 млн строк, полного сценария VoiceOver и RAM/временного диска в этом ручном прогоне не выполнялись.

## Дополнительная нагрузка 6000 × 4000: ошибка схемы

Для более длительной операции создан `/private/tmp/csv-ci-3aaaa24/manual-wide-cancel.csv`: исходные 600 записей повторены десять раз, заголовок записан один раз. Размер **2 469 773 890 байт**, SHA-256 **`653c3bb04087b66e5474a1d73e762e1c481c099b73869622c581a2d2fa68ac00`**. Искусственные задержки и подмена worker не использовались.

Открытие в том же CI-bundle `3aaaa24` завершилось OOM DuckDB ещё до получения страницы: `could not allocate block of size 30.5 MiB (491.2 MiB/512.0 MiB used)`, запрос `SELECT * FROM read_csv(...)`. После закрытия сообщения неуспешная вкладка удалена, прежний документ остался доступен. Активная отмена на этом файле не проверена: операция сортировки/unique не была запущена.

Открыт отдельный этап `bound-wide-csv-schema-detection` для ограничения получения схемы и проверки статистики до маршрутизации в потоковый backend. Это новая граница проверенной длины широкого файла, отдельная от завершённых backend-замеров 600 × 4000.

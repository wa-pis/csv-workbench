# Замеры операций широкого CSV — 2026-11-25

Проверены backend сортировки, запросов с правками, unique, Save и отмены на контрольном CSV **600 × 4000**. Бюджет DuckDB остался **512 MiB**; полные строки сортируемого представления хранятся на временном диске, а в DuckDB передаются узкие ключи. Точные значения сохранены в [benchmarks.json](benchmarks.json), воспроизводимый измеритель — [scripts/benchmark_wide_csv.py](../../../../scripts/benchmark_wide_csv.py).

## Источник и среда

- macOS 26.6.2, Apple Silicon arm64; Python 3.12.13, DuckDB 1.5.6.
- Исходник содержит **600 строк данных и 4000 столбцов**, **242 422 890 байт**. Заголовки `n0`…`n3999`; каждое значение — строка из 100 ASCII-цифр: `1234567890`, повторённое 10 раз. Формат — UTF-8 без BOM, разделитель `,`, заголовок включён, окончания записей LF.
- SHA-256: `6f2b1292a23fa78771413339aa5480cdc52df23603dba64152371314b4d280de`. После всех операций размер и хеш источника не изменились; в JSON записано `source_unchanged=true`.
- DuckDB использует производственный лимит **512 MiB**. Кэш соединения SQLite — **8 MiB**, `mmap_size=0`, временные данные SQLite направляются на диск. В узком Parquet для сортировки находятся идентификатор и два ключа, для unique — один выбранный столбец.
- Каждая операция выполняется в новом отдельном процессе; импорты предшествуют таймеру операции. Файловый кэш ОС не сбрасывался, источник повторно читался между операциями. Это один прогон на операцию на прогретом файловом кэше, без оценки разброса.

## Методика

Таймер `perf_counter` охватывает подготовку результата и его чтение/очистку. Для `sort` и `edited-sort` в него входят подготовка дискового представления, чтение страницы с offset 0, чтение страницы с offset 400 и удаление результата. Каждая страница содержит 200 строк с полным payload и префиксом идентификатора. Скрипт проверяет 4001 заголовок, число строк и граничные идентификаторы; сами значения широких строк дополнительно проверяются unit-тестами. Сортировка использует `n0 ASC`, затем `n3999 ASC`: в исходнике оба ключа одинаковы, поэтому отдельно проверяется стабильный порядок идентификаторов. В варианте с правкой ключ `n0` исходной строки 0 меняется на `z-edited`: первая позиция становится строкой 1, последняя — строкой 0.

`unique` выполняется по `n0` без правок. Это намеренно столбец с низкой кардинальностью: проверяется одна строка результата со значением из 100 цифр и частотой **600**. Измерение не характеризует unique при большом числе различных значений.

`save` включает полную запись, атомарную публикацию и получение новой ревизии. Переданы три правки: значение первого поля первой строки `edited`, явный NULL последнего поля строки 599 и новая строка с первым полем `added`. Опубликованный CSV имеет **601 строку данных** и размер **247 235 303 байта**. Последующее потоковое чтение проверяет ширину заголовка, число строк 601 и первое/последнее изменённые значения **после** фиксации времени и RSS; оно не входит в эти показатели. Точность NULL/empty проверяется отдельными unit-тестами: стандартный `csv.reader` этого контрольного чтения сам по себе их не различает.

RSS снят через `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss` до дополнительной проверки сохранённого файла. На macOS он задан в байтах; MiB рассчитаны делением на `2**20`. Это максимум процесса за время его жизни, включая импорты, а не только прирост внутри таймера. **Лимит DuckDB 512 MiB не является ограничением RSS Python/SQLite/Polars или всего настольного приложения.**

Родитель опрашивает файлы отдельного `TMPDIR` каждые **10 мс**, пока дочерний процесс не завершится. Исходный CSV и окончательный опубликованный `saved.csv` исключены; временный файл атомарной записи и промежуточные SQLite/Parquet включены. Таблица показывает максимальный **наблюдавшийся** объём: опрос может пропустить кратковременный пик между отсчётами, поэтому это не точный максимум файловой системы. Временный диск измеряется и во время дополнительной проверки Save, но её опубликованный выход исключён.

Для сортировки полный payload и узкие ключи дают наблюдавшийся пик временного диска **236.7 MiB**. Это дисковая материализация текущей выборки, а не заявление об отсутствии временных копий. У unique наблюдались **736 байт** временных файлов; значение `0.0 MiB` в таблице — округление, а не нулевой расход. Для Save наблюдавшийся пик временного диска, включающий промежуточный файл атомарной записи, составил **246 819 396 байт (235.4 MiB)**; опубликованный файл в этот пик не включён.

## Точка отмены

В сценарии `cancel-sort` событие выставляется при получении первой строки из `iter_csv_rows`. После ожидания **50 мс** вызывается `Cancellation.cancel()`. От вызова отмены до получения `CancelledError` прошло **0.005503 с (5.503 мс)**; полное время сценария внутри дочернего процесса с обнаружением схемы, запуском фоновой задачи и ожиданием события — **1.174 с**. После завершения проверено отсутствие оставшегося `csv-wide-*` payload в рабочем временном каталоге.

Эта отмена относится к подготовке payload. Она **не доказывает** отмену именно активной фазы сортировки DuckDB и не является ручной проверкой отзывчивости GUI.

## Воспроизведение

Из корня репозитория создать источник с точным размером и хешем. Режим `x` предотвращает перезапись существующего файла:

```sh
.venv/bin/python - <<'PYCODE'
from pathlib import Path
import hashlib

source = Path('/private/tmp/csv-wide-4000-repro.csv')
row = ','.join(['1234567890' * 10] * 4000) + '\n'
with source.open('x', encoding='utf-8', newline='') as output:
    output.write(','.join(f'n{i}' for i in range(4000)) + '\n')
    for _ in range(600):
        output.write(row)
with source.open('rb') as data:
    digest = hashlib.file_digest(data, 'sha256').hexdigest()
assert source.stat().st_size == 242422890
assert digest == '6f2b1292a23fa78771413339aa5480cdc52df23603dba64152371314b4d280de'
print(source, source.stat().st_size, digest)
PYCODE
```

Измеритель принимает `SOURCE.csv REPORT.json` и последовательно запускает пять изолированных процессов:

```sh
.venv/bin/python scripts/benchmark_wide_csv.py \
  /private/tmp/csv-wide-4000-repro.csv \
  /private/tmp/wide-csv-query-performance.json
```

Повторные время, RSS и временный диск зависят от нагрузки, файлового кэша и среды. Записанный в репозитории JSON фиксирует исходный прогон; приведённая команда сохраняет новый отчёт отдельно.

## Границы проверки

Предыдущий диагностический опыт с широкой проекцией завершался OOM сортировки даже при бюджете DuckDB 4 GiB и RSS около 5.4 ГБ. Это [предшествующий диагностический опыт](../2026-11-25-fix-wide-csv-import-memory/design.md), а не baseline в текущем JSON и не прямое сопоставление времени одинаковых успешных операций.

Итоговый полный регрессионный прогон — **398 passed за 22.69 с**, включая native Cocoa. Ruff и строгая валидация всего OpenSpec прошли. Публичные широкие контракты, потребители выборки и реальная регрессия 4000 столбцов проверены unit-тестами.

Новых замеров на 5 и 20 млн строк не выполнялось. Этот отчёт не подтверждает ручной сценарий GUI, новую автономную сборку или CI, другие ОС, произвольную ширину/размер поля, unique высокой кардинальности или жёсткий общий предел RSS. Независимые backend сравнения файлов и редактора SQL остаются вне этапа.
